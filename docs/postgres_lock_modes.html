Postgres table-level lock modes

Lightest → heaviest. Each is a distinct named mode, not just "shared" or "exclusive."

1 ACCESS SHARE SELECT read
2 ROW SHARE SELECT FOR UPDATE / FOR SHARE read
3 ROW EXCLUSIVE INSERT, UPDATE, DELETE write
4 SHARE UPDATE EXCLUSIVE VACUUM, ANALYZE, CREATE INDEX CONCURRENTLY write
5 SHARE CREATE INDEX (non-concurrent) write
6 SHARE ROW EXCLUSIVE CREATE TRIGGER, some ALTER TABLE forms write
7 EXCLUSIVE REFRESH MATERIALIZED VIEW CONCURRENTLY write
8 ACCESS EXCLUSIVE ALTER TABLE, DROP, TRUNCATE, LOCK TABLE write

Our situation: pid 2753 held ACCESS SHARE (1) on news_articles. pid 5640 needed ACCESS EXCLUSIVE (8) for ALTER TABLE — the only lock that conflicts with #1. Once #8 was queued, Postgres blocked all new lock requests on that table, including new #1s from our SELECTs.
